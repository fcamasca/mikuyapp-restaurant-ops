# MikuyApp — Hito H1: Plan de pruebas

Cada ejecución registra fecha, responsable, commit, entorno y evidencia. “Automatizada” significa que un comando o script determina aprobado/fallido sin juicio visual; “técnica manual” requiere inspección de una persona técnica; “humana” valida comprensión y presentación.

| ID | Precondiciones | Pasos | Resultado esperado | Tipo |
|---|---|---|---|---|
| TP-01 — Repositorio | Construcción autorizada y Git disponible. | Consultar raíz Git, rama, remoto y archivos ignorados. | El repositorio se identifica como `mikuyapp`, usa `main`, tiene remoto esperado y no versiona `.env.local` ni artefactos. | Automatizada |
| TP-02 — Instalación limpia | Node compatible, npm y `package-lock.json` presentes; sin `node_modules`. | Ejecutar `npm ci`. | Dependencias se instalan desde el lockfile sin modificarlo ni fallar. | Automatizada |
| TP-03 — Entorno fijado | Repositorio creado. | Consultar versión de Node/npm y revisar `.nvmrc`, `package.json` y lockfile. | Node es 22 LTS `>=22.12.0`, npm es el gestor y el lockfile está versionado. | Técnica manual |
| TP-04 — TypeScript | TP-02 aprobada. | Ejecutar el script de validación TypeScript sin emitir archivos. | Termina con código 0 y sin errores de tipos. | Automatizada |
| TP-05 — Arranque local | Variables públicas válidas y TP-02 aprobada. | Iniciar Vite, abrir URL local y observar la página. | La aplicación carga y muestra la página técnica, sin pantallas operativas. | Técnica manual |
| TP-06 — Roles, estados y flujo | Cuatro documentos disponibles. | Comparar códigos de roles, estados de mesa/pedido y secuencia operativa. | Coinciden 4 roles, 4 estados de mesa, 8 estados de pedido y el flujo aprobado. | Técnica manual |
| TP-07 — Estructura | Proyecto creado. | Ejecutar verificación de rutas obligatorias y ausencia de módulos fuera de H1. | Existen páginas, componentes, servicios, tipos, datos, migraciones y seed; no hay Auth, Realtime ni módulos operativos. | Automatizada |
| TP-08 — Build y Tailwind | TP-02 y TP-04 aprobadas. | Ejecutar `npm run build` y una comprobación de `dist` y del CSS generado para una utilidad usada por la página. | Build finaliza con código 0, genera `dist` y contiene el estilo Tailwind esperado. | Automatizada |
| TP-09 — Migración limpia | Base Supabase vacía y herramienta de migraciones configurada. | Aplicar una vez el conjunto de migraciones desde cero y consultar historial. | Aplicación sin error; una versión registrada. No se exige ejecutar directamente el mismo SQL dos veces. | Automatizada |
| TP-10 — Constraints e índices | TP-09 aprobada y conexión SQL de prueba. | Ejecutar casos con rol/estado inválido, cantidad fraccionaria, cantidad cero, cantidad negativa, precio `<0`, pago `<=0`, código duplicado y FK inexistente; consultar índices. | Las cantidades fraccionarias, cero y negativas y cada otro dato inválido son rechazados; existen UNIQUE e índices de D-08. | Automatizada |
| TP-11 — Relaciones, nulabilidad e identidad | TP-09 aprobada. | Consultar los catálogos PostgreSQL para tipos, PK, FK, nulabilidad, defaults, identidad y reglas `ON DELETE`, sin insertar usuarios ni datos transaccionales. | Las diez tablas coinciden con D-07; `pedido.id` es `bigint GENERATED ALWAYS AS IDENTITY`; `pedido.creado_por`, `historial_estado.usuario_id` y `pago.usuario_id` son NOT NULL; las cuatro relaciones históricas usan `ON DELETE RESTRICT`; `historial_estado.estado_anterior` permanece nullable. La secuencia funcional se difiere a H3. | Automatizada |
| TP-12 — Contenido del seed | TP-09 aprobada; base sin datos demo. | Ejecutar seed y consultar conteos/códigos/estados, incluidas las tablas transaccionales. | Hay 4 roles exactos, 1 local, 6 mesas `LIBRE`, 5 categorías y al menos 10 productos válidos; no hay usuarios Auth, perfiles, pedidos, detalles, historiales ni pagos creados por el seed. | Automatizada |
| TP-13 — Idempotencia del seed | TP-12 aprobada. | Capturar conteos e identificadores, ejecutar seed de nuevo y comparar. | No aparecen duplicados; conteos e identificadores naturales permanecen estables. | Automatizada |
| TP-14 — Lectura anónima | TP-10–TP-13 aprobadas y clave pública disponible. | Consultar mediante API pública `local`, `mesa`, `categoria` y `producto`; intentar seleccionar una tabla transaccional. | Filas activas necesarias son legibles; la tabla transaccional no es accesible. | Automatizada |
| TP-15 — Estados de UI | Cliente conectado y datos demo disponibles. | Observar sucesivamente carga, éxito y resultado vacío controlado. | Cada estado se distingue y el éxito muestra mesas, categorías y productos demo. | Técnica manual |
| TP-16 — Errores controlados | Aplicación local disponible. | Probar variables ausentes/incorrectas y fallo de red. | Mensaje comprensible y accionable; la UI no se rompe ni muestra credenciales. | Técnica manual |
| TP-17 — Escrituras anónimas | TP-10 aprobada y clave pública disponible. | Intentar `INSERT`, `UPDATE` y `DELETE` por API pública en cada tabla legible y al menos una transaccional. | Todas las escrituras son rechazadas por privilegios/RLS y los datos no cambian. | Automatizada |

| TP-20 — Validación humana H1 | TP-18 aprobada. | Una persona abre la URL, identifica datos demo y estado de conexión, y ajusta el ancho para vista estrecha y amplia. | URL accesible, datos visibles, estado comprensible y visualización responsive básica sin desbordes críticos. | Humana |

## Criterio de salida

Las pruebas TP-01–TP-19 deben pasar y TP-20 debe registrar resultado humano. Las pruebas completas en celulares, tablet y PC corresponden a H6. Fallos se registran y corrigen antes de proponer H1 como terminado. Este documento no aprueba el spec ni marca H1 completado.
