# MikuyApp — Hito H1: Diseño técnico

## D-01 — Repositorio y herramientas

La construcción inicializa Git para el repositorio GitHub oficial `fcamasca/mikuyapp-restaurant-ops` del producto `mikuyapp`, usa `main` como rama principal y conecta el remoto GitHub autorizado. Se versionan `.gitignore`, `.nvmrc` con `22`, `package.json` y `package-lock.json`.

El administrador de paquetes es npm. La versión base es Node.js 22 LTS, como mínimo `22.12.0`. Vite es la herramienta de desarrollo y construcción, con la plantilla React + TypeScript; `npm run build` produce `dist`.

## D-02 — Estructura

```text
src/
  components/
  pages/VerificationPage.tsx
  services/supabaseClient.ts
  services/demoCatalogService.ts
  types/
  data/
  lib/
  App.tsx
  main.tsx
supabase/migrations/
supabase/seed.sql
Docs/h1/
```

Componentes en PascalCase; funciones y variables en camelCase; tipos explícitos en servicios. Una responsabilidad por módulo. Sin router, estado global ni capas reservadas para funciones futuras.

## D-03 — Tailwind

Tailwind CSS se integra al pipeline de Vite con su configuración compatible. Solo cubre estilos de la página técnica y un breakpoint responsive básico. No se crea sistema de diseño en H1.

## D-04 — Página técnica

`VerificationPage` muestra: aplicación cargada, estado de configuración/conexión, cantidad y muestra de mesas, categorías y productos activos. Maneja explícitamente `loading`, `success`, `empty`, `configuration-error` y `connection-error`. No ofrece formularios ni mutaciones.

## D-05 — Entorno y errores

El cliente usa `VITE_SUPABASE_URL` y `VITE_SUPABASE_PUBLISHABLE_KEY` —o el nombre de clave anon pública entregado por Supabase—. `.env.example` contiene nombres sin valores reales; `.env.local` se ignora. Falta de variables genera un mensaje accionable. Errores visibles y logs se normalizan y no incluyen claves, encabezados ni cadenas de conexión. `service_role` está prohibida en frontend, Git y Cloudflare Pages.

## D-06 — Códigos controlados

- Roles: `ADMINISTRADOR`, `MOZO`, `COCINA`, `CAJA`.
- Mesa: `LIBRE`, `OCUPADA`, `PEDIDO_LISTO`, `PENDIENTE_PAGO`.
- Pedido: `ABIERTO`, `ENVIADO`, `RECIBIDO_COCINA`, `EN_PREPARACION`, `LISTO`, `ENTREGADO`, `PAGADO`, `ANULADO`.
- Pago: `EFECTIVO`, `YAPE`, `PLIN`, `TARJETA`.

Se usan `CHECK` en H1 para estados y medio de pago; los roles son filas controladas de `rol` con `CHECK` de código.

## D-07 — Modelo relacional

PostgreSQL usa `gen_random_uuid()`, `timestamptz` y nombres `snake_case`. La migración define exactamente:

### `local`

| Columna | Definición |
|---|---|
| `id` | `uuid NOT NULL DEFAULT gen_random_uuid()`; PK |
| `codigo` | `text NOT NULL`; `CHECK (btrim(codigo) <> '')`; UNIQUE |
| `nombre` | `text NOT NULL`; `CHECK (btrim(nombre) <> '')` |
| `activo` | `boolean NOT NULL DEFAULT true` |
| `creado_en` | `timestamptz NOT NULL DEFAULT now()` |

### `rol`

| Columna | Definición |
|---|---|
| `id` | `smallint GENERATED BY DEFAULT AS IDENTITY`; NOT NULL; PK |
| `codigo` | `text NOT NULL`; UNIQUE; `CHECK` con los cuatro códigos de D-06 |
| `nombre` | `text NOT NULL`; UNIQUE; `CHECK (btrim(nombre) <> '')` |
| `activo` | `boolean NOT NULL DEFAULT true` |

### `perfil_usuario`

| Columna | Definición |
|---|---|
| `id` | `uuid NOT NULL`; PK y FK a `auth.users(id) ON DELETE RESTRICT` |
| `local_id` | `uuid NOT NULL`; FK a `local(id) ON DELETE RESTRICT` |
| `rol_id` | `smallint NOT NULL`; FK a `rol(id) ON DELETE RESTRICT` |
| `nombre` | `text NOT NULL`; `CHECK (btrim(nombre) <> '')` |
| `activo` | `boolean NOT NULL DEFAULT true` |
| `creado_en` | `timestamptz NOT NULL DEFAULT now()` |

H1 no inserta filas en `auth.users` ni `perfil_usuario`. Cuando un usuario tenga actividad histórica, se desactiva mediante `perfil_usuario.activo = false`; no se elimina físicamente.

### `mesa`

| Columna | Definición |
|---|---|
| `id` | `uuid NOT NULL DEFAULT gen_random_uuid()`; PK |
| `local_id` | `uuid NOT NULL`; FK a `local(id) ON DELETE RESTRICT` |
| `codigo` | `text NOT NULL`; `CHECK (btrim(codigo) <> '')` |
| `nombre` | `text NOT NULL`; `CHECK (btrim(nombre) <> '')` |
| `estado` | `text NOT NULL DEFAULT 'LIBRE'`; `CHECK` con estados de mesa D-06 |
| `activo` | `boolean NOT NULL DEFAULT true` |
| `creado_en` | `timestamptz NOT NULL DEFAULT now()` |

UNIQUE `(local_id, codigo)` y UNIQUE `(id, local_id)`.

### `categoria`

| Columna | Definición |
|---|---|
| `id` | `uuid NOT NULL DEFAULT gen_random_uuid()`; PK |
| `local_id` | `uuid NOT NULL`; FK a `local(id) ON DELETE RESTRICT` |
| `codigo` | `text NOT NULL`; `CHECK (btrim(codigo) <> '')` |
| `nombre` | `text NOT NULL`; `CHECK (btrim(nombre) <> '')` |
| `orden` | `integer NOT NULL DEFAULT 0`; `CHECK (orden >= 0)` |
| `activo` | `boolean NOT NULL DEFAULT true` |
| `creado_en` | `timestamptz NOT NULL DEFAULT now()` |

UNIQUE `(local_id, codigo)` y UNIQUE `(id, local_id)`.

### `producto`

| Columna | Definición |
|---|---|
| `id` | `uuid NOT NULL DEFAULT gen_random_uuid()`; PK |
| `local_id` | `uuid NOT NULL`; FK a `local(id) ON DELETE RESTRICT` |
| `categoria_id` | `uuid NOT NULL` |
| `codigo` | `text NOT NULL`; `CHECK (btrim(codigo) <> '')` |
| `nombre` | `text NOT NULL`; `CHECK (btrim(nombre) <> '')` |
| `precio` | `numeric(10,2) NOT NULL`; `CHECK (precio >= 0)` |
| `activo` | `boolean NOT NULL DEFAULT true` |
| `creado_en` | `timestamptz NOT NULL DEFAULT now()` |

UNIQUE `(local_id, codigo)`. FK compuesta `(categoria_id, local_id)` a `categoria(id, local_id) ON DELETE RESTRICT`, impidiendo mezclar locales.

### `pedido`

| Columna | Definición |
|---|---|
| `id` | `bigint GENERATED ALWAYS AS IDENTITY`; NOT NULL; PK y número visible del pedido |
| `local_id` | `uuid NOT NULL`; FK a `local(id) ON DELETE RESTRICT` |
| `mesa_id` | `uuid NOT NULL` |
| `creado_por` | `uuid NOT NULL`; FK a `perfil_usuario(id) ON DELETE RESTRICT` |
| `estado` | `text NOT NULL DEFAULT 'ABIERTO'`; `CHECK` con estados de pedido D-06 |
| `creado_en` | `timestamptz NOT NULL DEFAULT now()` |
| `enviado_en` | `timestamptz NULL` |

FK compuesta `(mesa_id, local_id)` a `mesa(id, local_id) ON DELETE RESTRICT`. `id` se imprimirá posteriormente como número de pedido; no se diseña aún el ticket.

### `detalle_pedido`

| Columna | Definición |
|---|---|
| `id` | `bigint GENERATED ALWAYS AS IDENTITY`; NOT NULL; PK |
| `pedido_id` | `bigint NOT NULL`; FK a `pedido(id) ON DELETE RESTRICT` |
| `producto_id` | `uuid NOT NULL`; FK a `producto(id) ON DELETE RESTRICT` |
| `cantidad` | `integer NOT NULL`; `CHECK (cantidad > 0)`; no admite fracciones |
| `precio_unitario` | `numeric(10,2) NOT NULL`; `CHECK (precio_unitario >= 0)` |
| `observacion` | `text NULL`; `CHECK (observacion IS NULL OR btrim(observacion) <> '')` |

### `historial_estado`

| Columna | Definición |
|---|---|
| `id` | `bigint GENERATED ALWAYS AS IDENTITY`; NOT NULL; PK |
| `pedido_id` | `bigint NOT NULL`; FK a `pedido(id) ON DELETE RESTRICT` |
| `estado_anterior` | `text NULL`; si no es nulo, `CHECK` con estados de pedido D-06 |
| `estado_nuevo` | `text NOT NULL`; `CHECK` con estados de pedido D-06 |
| `usuario_id` | `uuid NOT NULL`; FK a `perfil_usuario(id) ON DELETE RESTRICT` |
| `creado_en` | `timestamptz NOT NULL DEFAULT now()` |

`CHECK (estado_anterior IS NULL OR estado_anterior <> estado_nuevo)`.

### `pago`

| Columna | Definición |
|---|---|
| `id` | `bigint GENERATED ALWAYS AS IDENTITY`; NOT NULL; PK |
| `pedido_id` | `bigint NOT NULL`; FK a `pedido(id) ON DELETE RESTRICT`; UNIQUE |
| `importe` | `numeric(10,2) NOT NULL`; `CHECK (importe > 0)` |
| `medio` | `text NOT NULL`; `CHECK` con medios de D-06 |
| `usuario_id` | `uuid NOT NULL`; FK a `perfil_usuario(id) ON DELETE RESTRICT` |
| `pagado_en` | `timestamptz NOT NULL DEFAULT now()` |

## D-08 — Índices

Las PK y UNIQUE crean sus índices. Se agregan: `perfil_usuario(local_id)`, `perfil_usuario(rol_id)`, `mesa(local_id, estado)`, `categoria(local_id, activo, orden)`, `producto(categoria_id, activo)`, `producto(local_id, activo)`, `pedido(local_id, estado, creado_en)`, `pedido(mesa_id, estado)`, `detalle_pedido(pedido_id)`, `detalle_pedido(producto_id)`, `historial_estado(pedido_id, creado_en)` y `pago(pagado_en)`. No se agregan índices sin consulta prevista.

## D-09 — Seguridad mínima pública

La migración habilita RLS en las diez tablas. Revoca privilegios y acceso a secuencias del rol `anon`; luego concede únicamente `SELECT` sobre `local`, `mesa`, `categoria` y `producto`. Cada una tiene una política `FOR SELECT TO anon USING (activo = true)`. Las otras seis tablas no tienen política anónima. No se concede `INSERT`, `UPDATE`, `DELETE` ni uso de secuencias a `anon`.

Esta doble barrera —privilegios más RLS— permite la página técnica y rechaza escrituras con la clave pública. Las políticas de `authenticated` por rol, Auth y usuarios se diseñan en H2.

## D-10 — Migración y seed

Una migración versionada crea extensión, tablas, constraints, índices, RLS, políticas y grants sobre una base vacía. No se exige ejecutar la misma migración directamente dos veces; la herramienta de migraciones registra su aplicación.

`seed.sql` usa códigos naturales con `INSERT ... ON CONFLICT ... DO UPDATE` o `DO NOTHING`, en una transacción. Si se ejecuta dos veces conserva exactamente cuatro roles, un local, seis mesas, cinco categorías y al menos diez productos, sin duplicados. Los UUID de demo son estables cuando simplifican referencias. No crea usuarios Auth, perfiles ni datos de `pedido`, `detalle_pedido`, `historial_estado` o `pago`.

## D-11 — Cloudflare Pages

El proyecto Cloudflare Pages `mikuyapp` se conecta al repositorio GitHub oficial `fcamasca/mikuyapp-restaurant-ops`; comando `npm run build`, salida `dist`, versión Node compatible y variables públicas de producción. Se registra la URL resultante. La página publicada consulta el mismo entorno Supabase documentado.

## D-12 — Límite del diseño

H1 no implementa Auth, usuarios, políticas por rol, Realtime, transiciones, funciones transaccionales, pedidos operativos, cocina, caja, impresión ni reportes. Tampoco crea usuarios Auth ni datos transaccionales. La verificación funcional de la secuencia de `pedido.id` queda para H3, cuando existan usuarios y pedidos; H1 verifica su definición `bigint identity` en los catálogos PostgreSQL.
